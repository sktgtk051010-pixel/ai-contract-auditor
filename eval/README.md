# 效果评估

## 两个集合分开

| 集合 | 用途 | 规则 |
|---|---|---|
| `debug` | 调提示词、改输出格式 | 可以反复跑，改动后回来重测 |
| `eval` | 最终结论 | 提示词定稿后才能跑，只跑一次，不回头调 |

先跑 `debug`，把提示词改到稳定；再跑 `eval`，`eval` 的结果才写进报告。混着跑等于自己给自己泄题。

## 三个对比项

| 项 | 定义 | CSV 列 |
|---|---|---|
| 基线检出 | 只有 Slither 时能否发现 | `slither_detected` |
| LLM 提出 | LLM 是否提出相关假设 | `llm_flagged` |
| 人工确认 | 复核后是否成立 | `human_confirmed` |

## 填表口径

- `slither_detected`：该案例在 Slither 输出里是否有对应告警（`build/slither.json` 里搜得到）
- `llm_flagged`：LLM 输出里是否提到该案例的问题点（`build/llm_findings.json` 里搜得到）
- `human_confirmed`：你复核后是否确认为真问题
- 三者都是 `yes` / `no`，没跑就是 `TODO`

## 计算

```bash
python eval/run_eval.py
```

输出 `eval/eval_result.md`，含基线检出率、LLM 新增、误报、漏报、LLM 精确率。

## 结果怎么读（2026-11-10 实跑）

| 指标 | 数值 | 说明 |
|---|---|---|
| 案例数 | 5 | 全部来自 staking 的 SR-01~SR-07 |
| 基线检出 | 1（20%） | Slither 只发现了定点数截断 |

**两个口径不要混：**

- `eval_result.md` 里的「LLM 精确率 100%」只统计这 5 个案例，**不含** LLM 额外提出的误报
- 全量精确率见 `review/review.md`：15 个函数提出 13 条假设，4 条成立、9 条误报，**30.8%**

面试被问「误报多少」时，报 30.8%，不要报 100%。

## 案例怎么选

当前 5 个案例全部来自 `D:\Solidity-Projects\staking` 的 `SECURITY-REVIEW.md` §3 发现清单（SR-01~SR-07 中挑了 5 条）：

| 案例 | 对应条目 | 类型 | Slither 能否检出 |
|---|---|---|---|
| C-01 | SR-06 定点数先除后乘 | 精度 | 能（`divide-before-multiply` 4 条） |
| C-02 | SR-05 owner 为单一 EOA | 中心化 | 不能（不检查权限设计） |
| C-03 | SR-03 空池期预算沉淀 | 资金效率 | 不能（业务语义） |
| C-04 | SR-07 未结算转让丢加成 | 记账 | 不能（业务逻辑） |
| C-05 | SR-02 段数线性增长 gas | 效率 | 不能（工具不看 gas 增长趋势） |

**选这 5 个的原因**：基线只能检出 1/5，正好用来测"LLM 能不能补上业务语义类问题"。如果 LLM 一条都没补上，说明提示词或模型不行；如果能补上 2–3 条，这个项目就有了可讲的结论。

案例选取标准：

- 每个案例要有明确答案（报告里已有裁决），否则无法判断检出
- 有修复版本更好：修复版应当检不出，用来验证工具不会乱报
- 不要用自己编的案例，必须来自真实项目的真实问题
